# Review rubric

Implementers get this file in their brief so they know the bar before they start. Reviewers (Claude or Codex) review against it and nothing else. Severity: **blocker** breaks the build, tests or data; **major** leaves a criterion unmet or a check unable to catch what it claims to; **minor** is everything else worth fixing. Style nits are never major.

## 1. Spec fidelity
- Every acceptance criterion that code can satisfy is met, and a test exists that fails without the change.
- Deliverables are at the named paths. There are no unrelated changes, and nothing outside the task's scope (for example `src/` in a test-only task).

## 2. Checks that can fail
Applies to any test, eval, gate, threshold or benchmark in the diff.
- **Mutation probe.** Reviewers try at least two plausible regressions of the code under test in a scratch copy, never in the worktree, and report whether a check catches each one. Implementers include a test per gate that applies such a mutation and asserts the gate catches it, by showing the measured value drops, not just that the gate is red. The mutation test runs through the same measurement path as its gate: the same loop, statistic and correctness checks, on the same data. Share one helper that takes the code under test as a parameter; do not write a shortcut probe.
- **No padding.** Corpora and fixtures are varied and tagged by category, and each category is reported separately. A threshold must not pass because easy items dilute hard ones. Gates have a minimum-size floor, and an empty set never scores 100%.
- **Honest ground truth.** Expected values are worked out by hand from the input, never generated by running the code under test, and never adjusted to make a gate pass.
- **Thresholds and exclusions.** Every coverage exclusion or loosened threshold carries a reason that holds up. Check what the number is without it.
- **Baselines are pinned.** If a gate is marked as an expected failure (`it.fails`), a strict test also pins the current per-category values, so further regressions still fail CI.

## 3. When a gate fails
Classify each failing item as (a) a real defect in code outside this task's scope, (b) an error in this PR (ground truth, comparison, harness), or (c) ambiguous spec. Count each class. Only (b) counts against the PR. (a) becomes a follow-up task. (c) is a question for a person.

## 4. Later rounds
From round 2 on, the reviewer gets the previous findings. Check each one is truly resolved, not papered over, before looking for new problems. Focus on the fix commit (`git show <sha>`), but re-run the full checks.

## 5. Output (reviewers)
Write ONLY a JSON object matching `scripts/agents/review-schema.json` to the output path you are given, and return the same JSON. `verdict` is `approve` only when there are no blocker or major findings and `unmet_criteria` is empty. Include the (a)/(b)/(c) counts in `summary` when any gate fails.
